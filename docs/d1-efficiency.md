# D1 读取优化

## 架构与取舍

定时 Worker 只负责触发 Actions，来源抓取、实测调度和选址已在 Actions 执行。保留独立的 `cf-dnspod-state` 保存共享状态，继续使用 D1 的事务、租约和发布意图校验；不为节省少量写入另建 KV、缓存或其他数据库。

D1 的读取额度计算扫描行数，而不是只计算最终返回的记录。行内容大小不改变行数计量，新增索引则会增加相关写入。[Cloudflare 计量说明](https://developers.cloudflare.com/d1/platform/pricing/)。

本次修改集中在 `src/state.ts`：

- 最新两轮按每条线路分别查询，再合并最多八条结果。使用已有 `(line, started_at DESC)` 索引直接定位，避免窗口函数扫描历史后再截取。
- 完整测量报告仍保存在原表内。比较字段改由 Actions 在读取后整理，避免 D1 使用嵌套 `json_each` 展开每个探针。代价是每次快照传输最多八条完整报告；D1 不收取数据传输费，数据不写入公开日志。
- 滚动小时预算、历史查询和过期清理显式限定配置中的四条受管线路，以便复用同一个索引。线路集合来自 `LINES`，新增线路时必须同步维护配置、数据库线路约束及相关业务逻辑。
- 不添加表、字段或索引，无需数据库迁移，也没有新增运行时写入。

保留 30/15 分钟任务频率、完整首次测量结果、48 小时历史、两轮判定、冷却、滚动预算、冻结与租约、异常保持和写后验证。快照仍在一次事务中读取；原子发布时仍检查数据库中的最新两轮。

## 发布与观察

代码进入生产 `main` 后，后续 Actions 会取用新查询；本次无需执行数据库迁移或单独重新部署 Worker。回退代码即可恢复旧查询，数据格式保持兼容。

上线后通过 Actions 摘要的 `stateUsage.rowsRead` / `rowsWritten` 和 D1 次日完整统计观察效果。写入次数预期基本不变，实际读行受探测完成情况、切换次数和手工查询影响，不应把上述单次查询降幅直接当作全天承诺。

## 是否可以完全交给 Actions

2026-10-28 复核：来源抓取、Globalping 调度、结果整理、优选判断、DNSPod 更新和回读均由 Actions 执行。Worker 只触发任务；D1 承担跨任务保存和协调，不承担测速。

| 状态表 | 保存内容 | 下一次运行的用途 |
| --- | --- | --- |
| `line_state` | 当前 IP、候选 IP、来源时效、上次切换时间、备用地址 | 继续比较同一基准，执行冷却和候选有效期 |
| `probe_rounds` | 每轮探针结果、失败、运行状态、预留测试数 | 连续两轮判断、滚动小时预算、保留不完整轮次 |
| `tool_control` | 轮转位置、已领取时段、暂停发布、退避和运行租约 | 避免重复测试，协调 Actions 与本机维护 |
| `switch_history` | 切换意图、结果和验证状态 | 追踪修改，恢复执行中断后尚未确认的切换 |

当前 Ubuntu 托管 runner 每个任务使用新的运行环境，工作目录不能直接作为下一轮的持久状态。[GitHub runner 说明](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners)。因此去掉 D1 后仍须另存状态，不能只靠每次临时下载 IP 列表。

技术上可以用 GitHub artifacts 或专门状态分支替代 D1，但需要重新实现状态版本选择、运行中检查点、发布前意图保存和异常恢复，并统一本机命令与 Actions 的写入入口。现有 Actions concurrency 仅协调同组工作流，不协调本机直接执行的 `apply`、`probe`、`freeze` 等命令。Artifacts 可以持久保存文件，但随所属运行删除而删除；cache 不能修改已有内容，且定位是可重新生成的缓存，不适合作为此项目唯一的权威状态。[Artifacts 说明](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts) · [Cache 说明](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)。

当前建议保留已优化的 D1：计算交给 Actions，小型共享状态留在 D1。完全迁移可以减少 Cloudflare 用量，但会引入另一套状态存储与恢复代码；以目前的数据量和优化后读行，没有必要仅为移除数据库名称进行这次架构重写。
